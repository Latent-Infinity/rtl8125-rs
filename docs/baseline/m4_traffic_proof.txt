## Caveats / known limitations of this baseline

  - Link autonegotiated at 1Gbps/Full (not 2.5G). The dedicated "Realtek
    Internal NBASE-T PHY" driver's probe returns -EOPNOTSUPP, so the
    PHY framework falls back to genphy which doesn't advertise 2.5G.
    Reaching 2.5G requires either porting the chip-specific PHY config
    table from r8169_phy_config.c::rtl8125b_hw_phy_config or making the
    Realtek PHY driver's probe succeed. M5 work; tracked separately.

  - netdev->stats.{tx,rx}_{bytes,packets} are not populated by this
    driver (they read 0/0 in `ip -s link`). Real traffic IS flowing —
    iperf3 confirms — but we don't bump the sw stats. M5 work; tracked
    as part of the §15.2 counter-sharding refactor (task 45).

  - rmmod under in-flight TCP can wedge the chip (host link drops, our
    PHY teardown succeeds but the chip needs a power-cycle / VM reboot
    to recover). Recommended: ip link down + sleep → rmmod. Tracked as
    a residual M4-traffic finish task.

## Build + load discipline

  - host: `make` (kernel-build, NOT cargo). One module: r8125_rust.ko.
  - guest: `rsync src/ → /tmp/r8125_rust_build/; make`.
  - load order: `modprobe -r r8169; modprobe realtek; insmod r8125_rust.ko`.
    (realtek.ko is the PHY driver — must be loaded before our driver
    attaches the phy_device, or the bind fails with -EUNATCH.)
